# OSS 单向同步规格

Version: 1.0

> 核对基线：SuperWiki `0.8.3`。本文以当前工作树实现为准；“同步”特指阿里云 OSS 的**单向上传**，不等同于双向同步、云端工作区或备份恢复方案。工作区本地文件夹始终是事实来源。

## 范围与术语

- **本地工作区**：用户在 SuperWiki 中打开的文件夹。
- **远端对象**：OSS Bucket 内的对象；对象键为 `<prefix>/<相对工作区路径>`。`prefix` 为空时直接使用相对路径。
- **全量同步**：递归枚举工作区目录树并上传其中所有非目录条目。
- **增量上传**：Markdown 成功落盘或资源成功上传后，将对应文件加入延迟上传队列。

当前实现不从 OSS 列举、下载、删除或修改任何已有远端业务对象；“测试连接”会创建并随即删除一个临时测试对象。

## 一、已实现的功能

### 1. 配置、凭据与安全边界

1. 设置页提供区域、Endpoint、Bucket、远端目录（`prefix`）、AccessKey ID、AccessKey Secret、启用开关、保存配置、测试连接和立即同步操作。
2. 非密钥配置保存在应用配置目录的 `oss-sync.json`；AccessKey Secret 使用操作系统 Keyring 中服务名 `com.superwiki.app`、账户名 `oss-access-key-secret` 的条目保存，配置文件不会写入 Secret。
3. 读取配置时旧配置缺少 `enabled` 字段会按 `false` 处理；首次保存或启用前必须补全区域、Endpoint、Bucket、AccessKey ID 和 Secret。
4. Endpoint 去除尾部 `/`；未带协议时自动补为 `https://`，显式指定的协议只接受 `http` 或 `https`。远端目录会去除首尾 `/`、将 `\\` 规范为 `/`，并拒绝含 `..` 的路径段。
5. 同步前端通过 Rust 命令读取文件字节，Rust 侧会规范化本地工作区根和目标路径并验证目标是工作区内既有普通文件。因此前端传入 `../` 或指向根外的符号链接，不能据此读出根目录外的文件。
6. OSS 客户端由 `ali-oss` 创建，固定启用 TLS（`secure: true`）和 OSS V4 签名（`authorizationV4: true`）。发起上传时，Secret 会从 Keyring 传入前端运行时内存以创建 SDK 客户端；它不落入 `localStorage` 或 JSON 配置。

### 2. 同步流程与触发条件

| 场景 | 当前行为 | 成功提示 / 失败处理 |
| --- | --- | --- |
| 保存配置 | 将非密钥字段写入 `oss-sync.json`；若填写了 Secret 则先写入 Keyring，空 Secret 保留已有值 | 显示“OSS 配置已保存”或错误文本 |
| 测试连接 | 先保存当前表单，再上传 `.superwiki-connection-test-<UUID>`，随后删除该对象 | 显示“OSS 连接正常”或错误文本 |
| 首次启用 | 先保存并启用配置，调用非强制的待保存刷新，刷新工作区树，递归上传所有文件 | 显示“同步完成，已同步 N 个文件”或错误文本；关闭自动保存时不会落盘当前草稿 |
| 立即同步 | 调用非强制的待保存刷新，再刷新工作区树，递归上传全部文件 | 显示“已同步 N 个文件”或错误文本；关闭自动保存时上传磁盘上的当前版本，而非编辑器草稿 |
| Markdown 自动保存 | 本地写入成功后，将该 Markdown 路径放入待上传集合 | 2 秒去抖后上传；显示已同步数量或错误文本 |
| 手动保存、切换前保存、更新前保存等显式落盘 | 复用同一入队逻辑 | 同上 |
| 图片或 HTML 资源上传 | 资源文件成功写到当前 Markdown 同级的 `assets/` 后，将该资源路径放入待上传集合 | 2 秒去抖后上传；同时刷新本地目录树 |

补充行为：

1. 自动上传只在同步已启用且 Keyring 中存在 Secret 时生效。待上传路径以 `Set` 去重；同一 2 秒窗口内的重复保存只传一次同一路径。
2. 全量同步使用一次 OSS 客户端，并通过 `Promise.all` 并发读取和上传所有文件。自动上传则对每个待上传文件分别建立客户端并并发上传。
3. 上传内容是文件原始字节，不限 Markdown；因此全量同步会覆盖工作区下的图片、HTML、Office 文件及其他普通文件对应的远端对象。对象键不包含本地绝对路径，只包含配置的 `prefix` 与相对路径。
4. 本地 Markdown 的自动保存默认另有 1 秒去抖和串行保存队列；OSS 上传只会在该本地写入成功之后进入队列，避免上传尚未落盘的 Markdown 内容。
5. 同步状态只有 `idle`、`syncing`、`error` 三种，界面展示聚合状态和文本，不展示文件级进度、对象 URL 或传输速率。

### 3. 可验证的实现边界

- 远端上传的基础实现位于 [ossSync.ts](/Users/administrator/cp/project/superwiki/src/ossSync.ts)，界面和触发逻辑位于 [App.tsx](/Users/administrator/cp/project/superwiki/src/App.tsx)，配置、Keyring 和工作区读取命令位于 [lib.rs](/Users/administrator/cp/project/superwiki/src-tauri/src/lib.rs)。
- 前端依赖锁定的 `ali-oss` 版本为 `6.23.0`；Rust Keyring 依赖为 `3`，并启用了 `windows-native` 特性。
- 当前工作区没有同步专用的测试用例、远端清单、数据库或后台常驻任务。应用退出后，尚未执行的 2 秒自动上传定时器和内存中的待上传集合都会丢失。

## 二、可以丰富的功能与当前取舍

以下项目是当前**未实现**的能力，不应被产品描述为已支持。

| 能力 | 当前取舍与原因 | 若要实现，需要先定义 |
| --- | --- | --- |
| 双向同步 / 从 OSS 恢复 | 仅上传，避免在没有冲突模型时以远端内容覆盖本地笔记 | 首次拉取策略、远端是否为事实来源、离线行为 |
| 冲突检测与合并 | 没有对象版本、ETag、mtime 或内容哈希比较；最后一次上传会覆盖同键对象 | 冲突判定、Markdown 合并规则、二进制文件处理和用户决策界面 |
| 删除与重命名同步 | 本地删除、重命名不会删除或移动远端对象；全量同步也只上传，不做远端清理 | 删除墓碑、保留期、误删恢复、重命名是否保留历史 |
| 版本历史与回滚 | OSS 中仅保留当前对象键所指向的版本（是否启用 Bucket 版本控制由用户侧决定，应用不配置） | 版本保留策略、浏览与恢复入口、存储成本上限 |
| 多端账号与共享 | 无账号、设备标识、权限模型或远端工作区发现机制 | 身份认证、授权、共享协作及审计模型 |
| 后台可靠投递 | 无持久化队列、重试、断点续传或启动补偿；失败仅停留在界面错误状态 | 任务持久化、退避重试、网络变化处理和失败告警 |
| 同步选择与排除 | 全量同步所有非目录文件；没有 `.gitignore` / `.superwikiignore`、大小上限或文件类型白名单 | 忽略规则优先级、隐藏文件和符号链接策略、超大文件处理 |
| 细粒度可观测性 | 只有总文件数和最后一条错误；无对象级结果、日志导出、用量或耗时 | 隐私边界、日志保存位置与清理策略 |
| 临时凭据与最小权限 | 使用用户填写的静态 AccessKey；实现简单但凭据长期有效 | STS / RAM 最小权限、刷新、失效与多平台 Keyring 兼容策略 |

特别说明：使用同一个 Bucket 与 `prefix` 为多个工作区同步时，具有相同相对路径的文件会映射到相同对象键，可能相互覆盖。当前实现把命名空间隔离交给用户配置，而不是自动加入工作区 ID。

## 三、设计与实现中的优化点

以下为基于代码行为的改进建议，不代表当前已实现。

### P0：可靠性与数据语义

1. **建立持久化上传队列与重试策略。** 将成功本地写入的路径、重试次数和最后错误持久化；应用启动时恢复未完成任务，采用指数退避和可见的“重试全部 / 重试单项”。这能解决退出、断网和短暂 OSS 故障导致的静默漏传。
2. **串行化同一工作区的同步批次。** 目前全量同步、2 秒增量上传和后续保存可能并行写入同一对象。应为每个工作区设置单一协调器：全量任务与增量任务合并、按路径去重，并保证较新的本地版本最后提交。
3. **在启用双向能力之前先定义冲突和删除模型。** 不建议直接增加下载按钮；没有 ETag / 版本 / 内容哈希和用户确认的下载，会使“同步”变成不可控的本地覆盖风险。
4. **为上传结果保存可校验元数据。** 至少记录远端 ETag、对象版本（如 Bucket 开启版本控制）、本地哈希和上传时间；全量同步完成后按需要 HEAD 校验，才能支持可靠的差异同步、诊断和恢复。

### P1：性能、成本与产品体验

1. **限制全量同步并发度并流式传输大文件。** 当前 `Promise.all` 会同时读取全部文件并构建 `Blob`，大工作区可能造成内存、网络连接和 OSS 请求突发。可采用受限并发队列、文件大小阈值和单文件进度。
2. **差异化上传。** 在有可靠元数据后，跳过哈希或 ETag 未变化的文件；同时提供忽略规则、文件大小限制和上传前汇总，减少带宽、请求次数和对象存储成本。
3. **完善进度与错误反馈。** 显示“已完成 / 总数”、当前文件、可重试文件数和具体失败原因；避免只显示一个聚合错误，尤其是在全量并发中无法识别已成功的部分。
4. **隔离远端命名空间。** 启用时可建议或自动生成稳定的工作区 ID 作为默认 `prefix`，并在修改前预览对象键，降低多个工作区覆盖风险。
5. **使连接测试无残留。** 当前测试对象的删除失败会留下对象；应在状态中告知残留键并提供清理，或使用具备生命周期规则的专用测试前缀。

### P2：安全与可维护性

1. **优先采用 STS / RAM 最小权限。** 静态 AccessKey 放在 Keyring 优于写入配置文件，但仍需进入 WebView 运行时，且长期密钥权限常超出同步所需。应限制为指定 Bucket、指定前缀的对象读写权限，并评估短期凭据刷新流程。
2. **减少凭据跨层暴露。** 可将 OSS SDK 调用下沉到 Rust，由前端仅传递同步请求和进度事件；这会增加 Rust SDK 与跨平台实现成本，但可避免将 Secret 交给 WebView JavaScript。
3. **将配置写入视为跨存储事务。** 当前 Secret 可能先写入 Keyring、再写 JSON；后一步失败时两处状态可能不一致。应设计补偿、状态标记或下一次启动修复流程。
4. **补充自动化测试。** 至少覆盖对象键生成、前缀与 Endpoint 规范化、缺少 Secret、路径越界拒绝、启用后的首次全量同步、2 秒去抖去重、部分上传失败、删除/重命名不传播等场景，并使用可控的 OSS 客户端替身验证调用顺序。

## 验收口径

本版本的可验收结论是：用户配置并启用 OSS 后，应用可将当前工作区磁盘上已有文件上传至指定 Bucket/前缀；之后 Markdown 成功本地保存以及图片、HTML 资源成功上传，会在约 2 秒的去抖后上传对应文件。关闭自动保存时，立即同步与首次启用不会强制保存当前编辑器草稿。它不保证离线最终送达，不支持从 OSS 下载、跨设备合并、远端删除同步或历史恢复。
