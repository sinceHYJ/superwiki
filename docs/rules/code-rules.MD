# 代码注释规范

## 1. 目的

本文规定 SuperWiki 代码注释的最低要求，帮助维护者快速理解文件、数据结构、函数接口以及关键业务逻辑。注释应说明“为什么这样做”和“这段代码负责什么”，不能只重复代码本身已经表达的内容。

## 2. 基本原则

- 注释应准确、简洁，并与代码保持同步；代码修改后必须同步更新受影响的注释。
- 注释使用中文，专有名词、API 名称、类型名和代码标识符保留原文。
- 注释应优先解释作用、约束、业务规则和设计原因；不要写无法验证的推测。
- 注释不能代替清晰的命名、合理的函数拆分或类型定义。
- 临时方案、已知限制和容易被误改的约束必须明确注明原因；问题解决后及时删除过时注释。

## 3. 文件级注释

每个源代码文件的顶部必须有文件级注释，明确说明该文件的作用和职责。至少包含：

- 文件负责的功能范围；
- 主要导出内容或对外提供的能力；
- 重要的边界、依赖或使用限制（如有）。

示例：

```ts
/**
 * 文件作用：提供工作区文件树的渲染和节点交互逻辑。
 * 对外能力：导出文件树组件和节点类型定义。
 * 限制：文件读取和写入必须通过 Tauri Rust 命令完成。
 */
```

## 4. 函数级注释

每个定义的函数（包括普通函数、箭头函数、方法、异步函数和闭包形式的对外逻辑）必须有函数级注释。注释必须说明：

- 函数的作用和使用场景；
- 每个入参的含义、类型约束和特殊取值；
- 出参的含义、类型和可能表示的状态；
- 异常、错误结果或副作用（如文件读写、状态更新、事件触发等）。

示例：

```ts
/**
 * 读取工作区中的 Markdown 文件内容。
 * @param root 工作区根目录的绝对路径。
 * @param path 待读取文件的绝对路径，必须位于 root 内且扩展名为 .md 或 .markdown。
 * @returns 文件的 UTF-8 文本内容。
 * @throws 当路径越界、文件不存在或读取失败时抛出错误。
 */
async function readWorkspaceFile(root: string, path: string): Promise<string> {
  // 通过 Rust 文件服务校验路径并读取内容，避免前端直接访问本地文件系统。
  return invoke<string>('read_workspace_file', { root, path });
}
```

对于回调、事件处理函数和内联函数，如果其逻辑包含业务判断、状态变化、文件操作或非显而易见的副作用，也必须补充注释；仅用于表达简单展示逻辑且语义完全清晰的单表达式函数可以省略，但不得省略其所在对外函数的说明。

## 5. 类型、常量和成员注释

### 5.1 函数、文件和枚举

文件级、函数级定义和枚举类型必须有注释。枚举的每个值必须说明其业务含义、使用场景以及与其他值的区别（如果区别不明显）。

```ts
/** 当前编辑器的显示模式。 */
enum ViewMode {
  /** 仅显示所见即所得编辑器。 */
  Editor = 'editor',
  /** 同时显示编辑器和 Markdown 预览。 */
  Split = 'split',
  /** 仅显示 Markdown 预览，不提供编辑入口。 */
  Preview = 'preview',
}
```

### 5.2 结构体、类和接口

结构体、类、接口、类型别名等复合类型必须说明整体用途；其中每个字段、属性和类变量必须说明存储的内容、单位或取值范围，以及为空或特殊值的含义。

```rust
/// 工作区目录树，表示用户当前选择的本地文件夹及其内容。
struct WorkspaceTree {
    /// 工作区根目录的规范化绝对路径。
    root: String,
    /// 工作区根目录的显示名称。
    name: String,
    /// 根目录下的直接子节点，按目录优先、名称排序。
    children: Vec<FileTreeNode>,
}
```

### 5.3 字典、Map 和键值集合

字典、`Map`、对象字面量和其他键值存储必须说明：

- key 存储的是什么、格式是什么，以及是否唯一；
- value 存储的是什么、类型是什么，以及与 key 的对应关系；
- 生命周期、默认值和缺失 key 时的行为（如有）。

```ts
/**
 * 语言标识到按需加载解析器的映射。
 * key：代码块使用的语言名称，统一使用小写标识符。
 * value：对应语言的异步解析器加载函数；缺少 key 表示暂不支持该语言。
 */
const languageLoaders: Map<string, () => Promise<LanguageSupport>> = new Map();
```

### 5.4 常量和重要变量

影响业务规则、时间、尺寸、路径、权限、缓存或状态流转的常量和变量必须说明其含义、单位和特殊值。纯局部且名称已充分表达含义的临时变量可以不单独注释。

## 6. 函数内部注释

函数内部的关键步骤和判断必须写明注释，尤其是以下情况：

- 路径规范化、权限校验、安全边界和输入过滤；
- 状态切换、异步流程、竞态处理和保存时序；
- 条件分支背后的业务规则或异常处理原因；
- 数据转换、排序、去重、缓存和性能优化；
- 与第三方库、Tauri IPC 或系统能力交互的特殊要求。

注释应放在对应代码之前，并说明判断依据或目的，而不是只写“判断是否为空”“遍历列表”等代码表面行为。

```ts
// 切换文件前先同步编辑器内部尚未通过更新事件上报的内容，避免快速点击导致最后一次输入丢失。
await syncEditorContent();

// 只有内容实际发生变化时才写盘，避免切换文件或重复触发更新造成无意义的文件修改。
if (content !== loadedContent) {
  await flushPendingSave();
}
```

## 7. 注释检查清单

提交代码前，至少确认：

- 文件顶部已说明文件作用和职责；
- 每个函数已说明作用、入参、出参、错误和副作用；
- 文件级、函数级定义和枚举值均有注释；
- 结构体、类、接口的字段和变量已说明存储内容；
- `Map`、字典等键值集合已分别说明 key、value 及对应关系；
- 函数内关键步骤和判断已说明原因或业务规则；
- 注释与当前实现一致，没有过时、重复或无法验证的描述。
